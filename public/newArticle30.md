## はじめに

個人開発しているWebアプリ「mojica」で、AIを活用したテスト駆動開発（TDD）を試してみました。

その結果、デプロイ後の手動確認をかなり減らすことができました。

一方で、AIが生成したテストケースやコードのレビューは、思った以上に大変でした。

今回は、AIを活用したTDDを通して感じた良かったことや困ったこと、レビューの負荷を減らすために取り組んだことについて紹介します。

## mojicaとは

mojicaは、推し活で使うことを目的に開発した、文字アート画像を生成するWebアプリです。

https://mojica.pages.dev/

好きな文字や色を指定して、文字アート画像を生成できます。Xのアイコンや背景画像にも対応しています。

まずはアプリの画面です。

![mojica](https://qiita-image-store.s3.ap-northeast-1.amazonaws.com/0/2284906/304c95f8-4955-4469-96b6-737e9d5faee8.png)

生成すると、例えば次のような画像を出力できます。

![mojicaで生成した画像](https://qiita-image-store.s3.ap-northeast-1.amazonaws.com/0/2284906/0e675013-5a45-4e1e-810d-4a869dac9441.png)

アプリ本体は、主に以下の技術で構成されています。

| 領域            | 技術         |
| --------------- | ------------ |
| フロントエンド  | React        |
| バックエンドAPI | ASP.NET Core |
| 外部API         | Python       |

今回、AIを活用してTDDに取り組み、コードレビューを行ったのは、ReactのフロントエンドとASP.NET CoreのバックエンドAPIです。

テストケースのレビューは両方で行いましたが、実装後のテストやコードについては、主にフロントエンド側を中心に確認しました。

## AIを活用したTDDの進め方

開発は、次の流れで進めました。

![tddの進め方](https://qiita-image-store.s3.ap-northeast-1.amazonaws.com/0/2284906/84fe0e91-c118-4940-a9c4-08d1776cf9d1.png)

1. AIにテストケースを作成してもらう
2. 作成されたテストケースをレビューする
3. AIを活用してTDDで実装する
4. 実装後にテストやコードをレビューする

まず、AIにテストケースを作成してもらい、その内容を人間がレビューしました。

テストケースを確認した後は、TDDで実装を進め、実装後のテストやコードについてもレビューしました。

このように、AIにすべてを任せるのではなく、人間がレビューを挟みながら開発を進める形です。

## TDDで良かったこと

実際にAIを活用してTDDを進めてみて、良かったと感じたことがあります。

一番良かったのは、**デプロイ後の手動確認がかなり減ったこと**です。

![AI活用TDDで手動確認を削減](https://qiita-image-store.s3.ap-northeast-1.amazonaws.com/0/2284906/599d480a-5f52-42ef-b81c-b9eebd02f111.png)

自動テストがあることで、毎回人間が画面や挙動を確認する作業を減らせました。

デプロイ後の確認にかかる時間を削減できました。

これはAIそのものというよりも、自動テストを整備したことによるメリットです。

AIを活用することで、そのテスト作成やTDDの実装を進められた点は良かったと感じています。

## でもレビューは大変だった

TDDによって手動確認は減った一方で、**レビューの負荷はかなり大きかった**です。

![レビュー負荷を示す](https://qiita-image-store.s3.ap-northeast-1.amazonaws.com/0/2284906/99156a42-28a5-4701-b76c-046544eacf18.png)

特に大変だったのは、レビュー対象の量が多いこと、期待しているコードやテストとのズレが多かったことです。

### 単純にレビューする量が多い

まず、レビュー対象の量が多いことです。

テストケースが多く、それに伴ってテストファイルも増えました。さらに、実装されたプロダクションコードの行数も多くなりました。

AIは大量のコードを生成できますが、人間がその内容を確認するには時間がかかります。

単純に読むだけでも時間がかかりますし、疲れます。

また、コードを読むだけではなく、実装の意図やテストの妥当性まで確認する必要があります。

そのため、コードを書いてもらう時間が短くなっても、その分レビューに時間がかかることがありました。

### 期待しているコードとのズレ

コードのレビューでは、例えば次のようなズレがありました。

- `i18n`で日本語と英語を切り替える処理のような分岐処理に、三項演算子が多用されている
- アロー関数を使ってほしいところで、`function` が使われている
- E2EテストでPage Object Model（POM）が使われていない

これらは必ずしも技術的に間違った実装というわけではありません。

三項演算子は、例えば、言語の切り替え処理の時に、日本語と英語だけなら、問題ないかもしれません。しかし、今後、言語が増えたときに拡張しづらくなります。

また、`function` を使うこと自体が問題なのではなく、今回の開発で期待していたコードスタイルと異なっていたことが問題でした。

さらに、E2Eテストについては、保守性を高めるためにPOMを使用してほしいのに、その構成になっていないコードが生成されることがありました。

こうしたズレがあるたびに、レビューで指摘する必要がありました。

### テストケースやテストコードにも問題があった

テストについても、さまざまな問題がありました。

- 重複したテストがある
- 「このテストはここで書かなくてもよくない？」と思うものがある
- 意味の薄いテストがある
- GoogleのTest Sizesを基準に分類していたが、分類が間違っている
- コードで再現できないテストケースが作成される

特に、テストの数が多いことと、テストの内容が適切であることは別だと感じました。

テストが大量に生成されても、同じことを何度も確認していたり、そのテストが置かれている場所に違和感があったりします。

また、GoogleのTest Sizesを基準にテストを分類していましたが、分類が誤っていることもありました。

テストケースとして書かれていても、実際にはその方法で再現できないものもありました。

こうした問題は、テストが実行できるかどうかだけでは判断できません。

**何をテストしているのか、そのテストが本当に必要なのかまで、人間が確認する必要がありました。**

## なぜレビューが重くなったのか

今回の開発を振り返ると、大きく2つの原因があったと思います。

![レビューが重くなった理由](https://qiita-image-store.s3.ap-northeast-1.amazonaws.com/0/2284906/9a9e3280-4bbb-4631-affa-6dc45027f86c.png)

### ルールを十分に示せていなかった

一つ目は、AIに対して開発上のルールを十分に示せていなかったことです。

例えば、以下のようなルールです。

- コーディングルール
- テストを書く基準
- 重複したテストを避ける基準
- どういうコードを書いてほしいか

こうしたルールを最初から十分に明示できていませんでした。

そのため、AIが生成したコードは動作として問題がなくても、自分が期待している実装とは異なることがありました。

### 対話しながら作る前提がなかった

二つ目は、テストケースをある程度まとめて作成してからレビューしていたことです。

テストケースを大量に作成してもらい、その結果を人間がまとめてレビューする進め方になっていました。

この方法では、途中で期待とのズレが発生していても、気づかないまま大量のテストケースが作成されてしまいます。

例えば、テストを書く基準について認識がズレていた場合、その基準に沿わないテストが複数作成される可能性があります。

結果として、**期待とズレた状態で生成されたものを、後からまとめてレビューする構造**になっていました。

最初に期待値を十分にすり合わせていなかったことに加え、途中で確認する機会も少なかったため、レビューの負荷が大きくなったのだと思います。

## レビューの負荷を減らすために取り組んだこと

レビューの負荷を減らすために、実際に取り組んだこともあります。

TSKaigiでの登壇で紹介されていた、**レビューで繰り返し出る指摘をLintやルールに戻す**というやり方を参考にしました。

レビューで出てきた指摘のうち、機械的にチェックできるものはLintやルールに追加しました。

例えば、コードスタイルに関する指摘は、人間が何度も指摘するのではなく、ルールとしてチェックできるようにするという考え方です。

その結果、同じコードスタイルについて何度も指摘するケースは減りました。

一方で、テストの必要性やテストケースの妥当性などは、Lintだけで判断できるものではありません。

そのため、機械的にチェックできるものは仕組みに任せ、人間はそれ以外のレビューに集中することが重要だと感じました。

## 次にやりたいこと

今後は、テストケースをまとめて大量に作成してからレビューするのではなく、途中で小さく確認しながら期待値をすり合わせたいと考えています。

その方法として、`grill-me`などを使ってみたいと思っています。

実装やテストケース作成の前に、AI側から質問してもらい、期待している仕様や実装方針をすり合わせるやり方です。

例えば、テストケースを作成する前に、何をテストすべきか、どの範囲までテストするか、どのようなテスト構成にするかを確認するイメージです。

そのうえで、いきなり大量のテストケースを作るのではなく、小さな単位で作成とレビューを繰り返したいです。

これによって、期待とのズレを早い段階で発見し、後から大量の修正が必要になる状況を減らせるのではないかと考えています。

まだ試していないため、実際にどこまで効果があるかは分かりませんが、取り組んでみたいです。

## まとめ

AIを活用したTDDによって、**デプロイ後の手動確認はかなり減らせました**。

一方で、レビューの負荷まで自動的に減るわけではありませんでした。

実際に、テストケースやコードの量が多いことに加え、期待とのズレがある状態で大量に生成されると、レビューの負荷がかなり大きくなりました。

その原因として、ルールを十分に示せていなかったことと、途中で期待値をすり合わせる機会が少なかったことがあると感じています。

レビューで繰り返し出てきた指摘をLintやルールに戻すことで、同じ指摘を減らすことはできました。

次は、テストケースを作る段階からAIとの対話を増やして、期待とのズレそのものを小さくしていきたいです。

今回の経験から、**AIに大量のコードを書いてもらうだけではなく、どうすれば人間がレビューしやすい形で開発を進められるかを考えることも大切**だと感じました。
